# LightPM

LightPM は、Claude Code が「次にやる作業」を規則で1件に決めるためのプラグインです。
スキル、サブエージェント、モッドを1つにまとめて配布します。

AI エージェントは、目の前の問題をその場で直し始めがちです。
その結果、基本機能（`max`）が未完成のまま軽微なバグ（`mid` 以下）に手を付け、重要な実装が後ろにずれます。
LightPM は、リリースフェーズ（Alpha → Beta → RC → GM）と優先度（`max` / `xhigh` / `high` / `mid` / `low` / `xlow`）から着手順を決めます。
今のフェーズで取り組まない作業は後回しとして記録し、フェーズが進むと自動で戻します。
作業中に気づいた別の作業は登録しておけば、優先度順に回ってきます。

- **選択は決定的**：同じ `.pm/` からは常に同じタスクが選ばれます。LLM を使うのは分類（種別と優先度）だけです。
- **人間の承認ゲートなし**：分解、優先付け、実装、完了の確認までを自走します。判断の理由は監査ログに残ります。
- **伝えるのは「今やること」**：Claude には禁止事項の一覧ではなく、今取り組むタスクと、気づいた作業の登録先を伝えます。
- **状態はすべてファイル**：`.pm/` 以下にテキストで置くので、git で追跡でき、セッションをまたいで再開できます。
- **実行時依存ゼロ**：TypeScript だけで書かれており、ビルド手順はありません。

## 必要なもの

- Claude Code 2.1.287 以降（モッドが使える版）

## インストール

マーケットプレイスとして追加する場合は、次を実行します。

```text
/plugin marketplace add YmSaki/cc-LightPM
/plugin install lightpm@cc-lightpm
```

手元のクローンをそのセッションだけで読み込む場合は、次のように起動します。

```sh
claude --plugin-dir /path/to/cc-lightpm
```

## 使い方

### 目的をタスクに分解する

```text
/lightpm:pm-plan TypeScript の CLI ToDo アプリ（追加、一覧、完了）を作る
```

目的を分解し、分類してタスクとして登録します。
まず端から端まで通る基本シナリオを1〜3本決め、それを構成するタスクを `max` にします。
残りはルーブリック（「規則」の節）で種別と優先度を決めます。
今のフェーズで取り組まないタスクは、登録した時点で後回しになります。

### タスクを順に実装する

```text
/lightpm:pm-run
```

次のループを回します。

1. `pm_next` が次のタスクを1件選ぶ
2. サブエージェント `pm-implementer` がそのタスクを実装し、JSON で報告する
3. `pm_complete` が完了条件をすべて満たしたかを確かめ、満たしていれば完了にする
4. 報告に含まれる「気づいた別の作業」（`discovered`）を `pm_add` で登録する

ループは「待ち」（着手できるタスクがない）、「完了」（GM の release タスクがすべて終わった）、同じタスクの2回連続の失敗のいずれかで止まります。
`/lightpm:pm-run 3` のように、1回に進める件数の上限も指定できます。
状態は `.pm/` にあるので、止まった後も次のセッションで続きから再開できます。

### 気づいた作業を登録する

```text
/lightpm:pm-triage ログイン画面で長いメールアドレスが切れる
```

作業中に気づいた問題や新しい依頼を、ルーブリックで分類して登録します。
着手する順番は、ほかのタスクと同じ規則で決まります。

### 状態を見る

プロンプトの上の帯に、フェーズ、作業中のタスク、残数が1行で表示されます。

```text
LightPM Alpha · ▶ T-0003 CLI エントリと add を実装する [max] · todo 3 · 後回し 1 · 完了 2  [ 一覧 ]
```

Claude には、毎回のプロンプトに、フェーズと今やるタスク、終わったら呼ぶツールの要約が600文字以内で渡ります。

`/pm` は、フェーズ、作業中のタスク、todo と後回しの一覧、次の候補、フェーズを抜ける条件の進み具合を表示します。
`/pm why T-0003` は、そのタスクが選ばれた理由や後回しになった理由を、監査ログから時系列で表示します。

### タスク一覧

`/pm view` を実行するか、帯の `[ 一覧 ]` を押すと、タスク一覧のペインが開きます。
タスクは `pm_next` が選ぶ順に並び、「次にやる順」の1番が次に取りかかるタスクです。
行を選んで Enter を押すかクリックすると、そのタスクでやること（完了条件）が展開されます。
Esc で閉じます。

```text
LightPM Alpha · 完了 2

作業中（1）
▸ T-0003 [max] CLI エントリと add を実装する

次にやる順（2）
▾ 1. T-0002 [low→max] 保存処理を整理する
      やること（完了条件）
      1. JSON の読み書きを store.ts にまとめる
      2. 既存のテストが通る
      種別 refactor · 前提 T-0001
      主なファイル: src/store.ts
▸ 2. T-0004 [high] list コマンド

前提の完了待ち（1）
▸ T-0005 [max] done コマンド

後回し（1）
▸ T-0006 [low] 色の調整
```

`[low→max]` は、元の優先度は `low` だが、`max` のタスクの前提になっているので実効優先度が `max` になっている、という意味です。

### `/pm` のサブコマンド

| コマンド | 内容 |
| --- | --- |
| `/pm`、`/pm status` | フェーズ、作業中のタスク、todo と後回しの一覧、次の候補、フェーズを抜ける条件 |
| `/pm view` | タスク一覧のペインを開く |
| `/pm init [phase]` | `.pm/` を作る（`pm_add` でも自動で作られる） |
| `/pm next` | 次に選ばれるタスクを表示する（状態は変えない） |
| `/pm list [status]` | タスクの一覧 |
| `/pm why <id>` | 選択、後回し、再分類の履歴 |
| `/pm phase` | 現在のフェーズを表示する |
| `/pm phase set <phase> [理由]` | フェーズを手動で変える（監査ログに `phase.set` として残る） |
| `/pm policy` | 現在のフェーズポリシーの表 |
| `/pm metrics` | 効果の指標を監査ログから集計する（「効果の計測」の節） (未) |
| `/pm refresh` | `.pm/` を読み直して帯と一覧を更新する |
| `/pm help` | サブコマンドの一覧 |

## 規則

### 優先度

| 優先度 | 意味 |
| --- | --- |
| `max` | 基本機能。欠けるとプロダクトの主目的が成立しない |
| `xhigh` | 主要シナリオの成立に必要。データ損失や重大なセキュリティ問題を含む |
| `high` | 重要。なくても使えるが、多くの利用者が困る |
| `mid` | 通常。影響が限定的、または回避策がある |
| `low` | 改善、見た目、軽微な不具合 |
| `xlow` | あれば良い。将来の候補 |

分類では、上の表を `max` から順に当てはめ、最初に合致したものを採ります。
判定が割れたら低い方を採ります。
後回しにした作業はフェーズが進めば戻せますが、先走った作業は戻せないためです。

### バグの優先度

バグの優先度は、影響を受ける機能の優先度と重大度の組み合わせで決まります。
重大度は、`S0` がデータ損失、クラッシュ、セキュリティ、`S1` が機能そのものが使えない、`S2` が回避策のある劣化、`S3` が外観や軽微な不具合です。

| 影響先の優先度 | `S0` | `S1` | `S2` | `S3` |
| --- | --- | --- | --- | --- |
| `max` | `max` | `max` | `xhigh` | `mid` |
| `xhigh` | `xhigh` | `xhigh` | `high` | `low` |
| `high` | `xhigh` | `high` | `mid` | `low` |
| `mid` 以下 | `high` | `mid` | `low` | `xlow` |

`impacts` に既存タスクの ID を指定すると、指定された `priority` よりこの表の値が優先されます。
影響先がタスクになっていない機能なら、その機能の優先度を `impact_priority` に渡します。
RC 以降に `xhigh` 以上のバグを登録または再分類すると、自動でリリース阻害（`release_blocker`）になります。

### フェーズごとの着手できる下限

タスクが今のフェーズで着手できるかは、種別と実効優先度が次の下限を満たすかで決まります。

| フェーズ | feature | bug | chore | refactor、polish | release |
| --- | --- | --- | --- | --- | --- |
| Alpha | `high` 以上 | `xhigh` 以上 | `mid` 以上 | `xhigh` 以上 | 不可 |
| Beta | `xhigh` 以上 | `mid` 以上 | `mid` 以上 | `high` 以上 | 不可 |
| RC | 不可 | `high` 以上、またはリリース阻害 | `high` 以上 | 不可 | 不可 |
| GM | 不可 | リリース阻害のみ | 不可 | 不可 | 可 |

下限に満たないタスクは `deferred`（後回し）になります。
そのとき、着手できる最初のフェーズ（`defer.until`）と理由（種別ごと不可なら `P-KIND`、優先度が足りなければ `P-FLOOR`）が記録されます。
どのフェーズでも着手できないタスクは `post`（リリース後）になります。

**実効優先度**は、依存を考慮した優先度です。
タスクは、自分に依存している未完了のタスクの優先度を引き継ぎます。
たとえば `max` のタスクの前提になっている `low` の refactor は、`max` として扱われ、Alpha でも先に選ばれます。
後回しの判定は `pm_next` のたびに見直すので、後回しのタスクが後から `max` のタスクの前提になった場合も、すぐ todo に戻ります。

### フェーズを抜ける条件

着手できるタスクがなくなると、`pm_next` はフェーズを抜ける条件を確かめます。
満たしていれば、人間の承認なしに次のフェーズへ進みます。

- **Alpha → Beta**：`max` と `xhigh` の feature が未完了ゼロ
- **Beta → RC**：`xhigh` 以上の feature と `high` 以上の bug が未完了ゼロ
- **RC → GM**：リリース阻害の bug と `high` 以上の bug が未完了ゼロ
- **GM**：release タスクがすべて完了したらプロジェクト完了

どの条件も、作業中のタスクがないことを前提にします。
1回の `pm_next` で、条件を満たす限り GM まで続けて進みます。
フェーズは前にしか進みません。
戻すときは `/pm phase set` を使い、その操作は監査ログに残ります。
タスクが1件もないときは、フェーズを進めずに登録を待ちます。

### 並べ替え

着手できるタスクは次の順に並べ、先頭を選びます。

1. 実効優先度（高い方が先）
2. 推移的に妨げているタスクの数（多い方が先）
3. フェーズの主役の種別（Alpha は feature、Beta と RC は bug、GM は release）
4. 見積（S、M、L、未設定の順）
5. 作成日時（古い方が先）
6. ID

最後の ID が順序を一意に決めるので、タスクの読み込み順に関係なく同じタスクが選ばれます。
前提のタスク（`depends_on`）がすべて `done` か `dropped` になるまで、そのタスクは選ばれません。

## Claude が使うツール

モッドが次のツールを登録します。
Claude からは `mcp__lightpm__pm_next` のような名前で見えます。

| ツール | 内容 |
| --- | --- |
| `pm_status` | 状態を返す（状態は変えない） |
| `pm_next` | 次のタスクを1件選んで作業中にし、実装者に渡すタスク契約を返す。作業中のタスクがあればそれを返す |
| `pm_add` | タスクを登録する。今のフェーズで着手できないものは後回しになる。`.pm/` がなければ作る |
| `pm_update` | タスクを更新、再分類する。理由が必須で、旧値と新値が監査ログに残る。`todo` への差し戻しと `dropped`（取り下げ）もここで行う |
| `pm_complete` | 実装者の報告を受け取る。完了条件をすべて満たしていれば完了にし、`failed` なら todo に戻す |

並行して呼ばれても、モッドの中で書き込みを1本の列に並べるので、タスクの ID は重複しません。

## `.pm/` の形式

状態はリポジトリ直下の `.pm/` にテキストで置きます。
git で追跡する想定です。

```text
.pm/
├── config.json        設定（フェーズポリシーの上書き）
├── state.json         現在のフェーズ、次のタスク番号、作業中のタスク
├── tasks/
│   └── T-0001.md      1タスク1ファイル（YAML frontmatter と本文）
└── log/
    └── 2026-10.jsonl  監査ログ（月ごと、追記のみ）
```

タスクファイルの例です。

```markdown
---
schema: 1
id: T-0003
title: CLI エントリと add コマンドを実装する
kind: feature
priority: max
status: todo
depends_on: [T-0002]
scope:
  paths: ["src/cli.ts", "src/commands/add.ts", "tests/add.test.ts"]
acceptance:
  - todo add <title> でタスクが保存され、追加した id を表示する
non_goals:
  - list と done の実装
estimate: S
created: 2026-10-02T00:18:04.101Z
updated: 2026-10-02T00:18:04.101Z
---

背景や再現手順などの自由記述。
```

| フィールド | 内容 |
| --- | --- |
| `id` | `T-` と4桁以上の番号。採番はモッドが行う |
| `title` | 1行のタイトル |
| `kind` | `feature`、`bug`、`refactor`、`polish`、`chore`、`release` |
| `priority` | `max`、`xhigh`、`high`、`mid`、`low`、`xlow` |
| `status` | `todo`、`in_progress`、`done`、`deferred`、`dropped` |
| `depends_on` | 実装上の前提になるタスクの ID。循環は拒否する |
| `scope.paths` | 主に触るファイルやディレクトリの目安（任意） |
| `acceptance` | 完了条件（1つ以上） |
| `non_goals` | このタスクに含めないもの（任意） |
| `estimate` | `S`、`M`、`L`（任意。並べ替えに使う） |
| `severity`、`impacts` | バグの重大度と影響先（bug で必須） |
| `release_blocker` | リリース阻害のバグか |
| `defer.until`、`defer.reason` | 後回しの解除先と理由 |
| `failures`、`notes` | 連続した失敗の回数と、直近のメモ |
| `created`、`updated` | 作成日時と更新日時 |

タスクは削除しません。
不要になったら `pm_update` で `dropped` にします。

`.pm/` は手で編集しても構いません。
ツールを呼ぶたびにディスクから読み直すので、手編集や `git pull` の後も読み込みの操作は要りません（帯と一覧をすぐ更新したいときは `/pm refresh`）。
読めないファイルは `/pm status` に理由とともに表示され、選択からは外れます。
モッドは `.pm/` の外へは書き込まず、書き込んだ後に読み戻して内容を確かめます。

### 設定

`.pm/config.json` の `policy` で、フェーズごとの着手できる下限を上書きできます。
変えたい項目だけを書きます。

```json
{ "schema": 1, "policy": { "alpha": { "bug": "mid", "polish": null } } }
```

値は優先度の名前で、`null` はその種別を不可にします。
`/pm policy` で、上書きを反映した表を確認できます。

### 監査ログ

状態の変化と選択は、すべて `.pm/log/YYYY-MM.jsonl` に追記されます。
各行には共通して `schema`、`ts`、`seq`（月内の連番）、`actor`、`event` が入ります。
`actor` は `core`、`main`、`subagent:<id>`、`user` のいずれかです。

| イベント | 記録するとき |
| --- | --- |
| `task.created` | 登録（分類の理由を含む） |
| `task.selected` | `pm_next` による選択（候補数、着手可能数、上位3件の並べ替えキー） |
| `task.deferred`、`task.restored` | 後回しにしたとき、todo に戻したとき |
| `task.reclassified` | 分類の変更（旧値、新値、理由） |
| `task.status`、`task.updated` | 状態の変更、そのほかの項目の変更 |
| `task.completed`、`task.incomplete`、`task.failed` | 完了、完了条件の不足、失敗 |
| `phase.advanced`、`phase.set` | 自動の昇格、手動の変更 |
| `agent.spawn` | サブエージェントの起動 |

導入の効果を、監査ログから次の指標で示します。

| 指標 | 定義 |
| --- | --- |

## モッドなしで使う

managed settings などでモッドが無効な環境でも、スキルとサブエージェントは動きます。
この場合、Claude は `pm_*` ツールの代わりに、上の形式で `.pm/tasks/` を直接編集します。
帯と一覧は表示されません。

選択の規則は Node から呼べる入口を通して適用するので、モッドがなくても同じタスクが選ばれます (未)。

## 構成

| 種類 | 名前 | 役割 |
| --- | --- | --- |
| スキル | `pm-plan` | 目的を分解し、分類して登録する |
| スキル | `pm-run` | `pm_next` から完了までのループを回す |
| スキル | `pm-triage` | 気づいた作業を分類して登録する |
| サブエージェント | `lightpm:pm-implementer` | 1タスクを実装し、JSON で報告する |
| モッド | `hooks/lightpm.tsx` | ツールとコマンドの処理、プロンプトへの要約の追加、帯、タスク一覧のペイン、監査ログ |

モッドが使う API は `$.fs`（`.pm/` の読み書きのみ）、`$.state`、`$.ui`、`$.tool`、`$.command`、`$.clock`、`$.session.root` です。
ネットワークも LLM も呼ばないので、モッドがプランや API キーを消費することはありません。
`claude plugin validate .claude-plugin/plugin.json` で、モッドが使う API の一覧を確認できます。

## 開発

```sh
npm test            # コアの単体テストとモッドのテストをまとめて実行
npm run test:core   # コアの単体テスト（node --test。Node 22.18 以降、Claude Code なしで動く）
npm run test:mod    # モッドのテスト（claude plugin test）
npm run validate    # マーケットプレイスとプラグインの定義の検証（claude plugin validate）
npm run typecheck   # 型チェック（tsc）
```

```text
src/core/              純粋関数（型、ポリシー、frontmatter、選択、一覧の並び、登録、更新、完了、文面）
src/io/                .pm/ の読み書き
hooks/                 モッドの入口
skills/、agents/       スキルとサブエージェント
types/                 モッドが $.state に置く値の型
tests/core/*.spec.ts   コアの単体テスト（表駆動、読み込み順を入れ替える性質テスト、性能）
tests/mod/*.test.ts    モッドのテスト（$.fs をメモリ上で置き換える）
```

型チェックには、Claude Code がモッドを読み込んだときに書き出す `.claude-plugin/types/` が必要です。
先に一度 `claude --plugin-dir .` で起動してください。

CI では、プルリクエストごとにコアの単体テストを回します。
モッドの検証（`claude plugin validate --strict` と `claude plugin test`）も、Claude Code の最小対応版と最新版の両方で回します (未)。
