# LightPM: 実行ループ

メインセッションは**調整に徹する**。コードは自分で編集せず、1タスクごとに `lightpm:pm-implementer` に渡す。メインのコンテキストにはタスクの要約と報告だけを残す。

最大タスク数: $ARGUMENTS（空なら「待ち」か「完了」になるまで続ける）

## ループ

1. `mcp__lightpm__pm_next` を呼ぶ。
   - 「待ち」なら、理由をそのまま人に報告してループを終える。
   - 「完了」ならプロジェクト完了を報告してループを終える。
   - フェーズが進んだら、そのことを1行で記録する。
2. 結果の「タスク契約」を**そのまま**プロンプトにして、Agent ツールで `subagent_type: "lightpm:pm-implementer"` を起動する。自分で要約したり範囲を広げたりしない。
3. 返ってきた JSON 報告を `mcp__lightpm__pm_complete` に渡す（`taskId`、`status`、`changedFiles`、`acceptance`、`discovered`、`notes`）。
   - **完了**: 次へ。
   - **完了にしていない（完了条件）**: 満たしていない条件を添えて、同じタスクを実装者にもう一度依頼する（新しい Agent 呼び出しでよい）。
   - **完了にしていない（範囲外の変更）**: 実装者に「範囲外のファイルの変更を元に戻し、その問題は discovered に書く」よう依頼する。範囲外の変更がタスクに本当に必要なら、`mcp__lightpm__pm_update` で `scope_paths` を広げる（`reason` 必須）か、別タスクに分けて `depends_on` を付ける。その後もう一度 `pm_complete`。
   - **失敗**: 1回目は次の `pm_next` で同じタスクが再び選ばれるので、そのまま続ける。「2 回続けて失敗」と返ったらループを止めて人に報告する。
4. 報告の `discovered` を1件ずつ、`/lightpm:pm-triage` のルーブリックで分類して `mcp__lightpm__pm_add` で登録する。**その場で直さない**。今のフェーズで着手できないものは自動で後回しになる。
5. 1 に戻る。

## 守ること

- タスクを選ぶのは `pm_next` だけ。自分の判断で別のタスクや「ついでの修正」に着手しない。
- 人への承認は求めない。判断の理由は監査ログ（`.pm/log/`）と `/pm why <id>` で追える。
- ループを終えるときは、完了したタスク、登録した発見、残り（todo・後回し）を短くまとめる。
- 状態は `.pm/` にあるので、途中で止まっても次のセッションで `/lightpm:pm-run` を呼べば続きから再開できる（作業中のタスクがあれば `pm_next` がそれを返す）。
