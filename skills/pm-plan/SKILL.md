# LightPM: 計画

目的: $ARGUMENTS

目的を、優先度の付いたタスクの集まりにする。**承認は求めない**。登録した内容は `/pm` と `/pm view` で確認できる。

## 手順

1. `mcp__lightpm__pm_list` で現状を見る。既にあるタスクと重複させない（`.pm/` がなくても `pm_add` が作る）。
2. 目的から**基本機能**を、端から端まで通る 1〜3 本のシナリオとして書き出す（例:「一覧を見て、CSV で保存する」）。そのシナリオが最後まで通るのに必要なタスクを `max` にする。
3. 残りを分解し、下のルーブリックで `kind` と `priority` を付ける。1タスクは、1回の作業で終わる大きさにする。
4. 各タスクに書く:
   - `body`: 何をするタスクかの説明（1〜3文）。
   - `checklist`: やること。済みにできる単位で、確かめられる形に分ける（1つ以上、必須）。
   - `reason`: その優先度にした理由を1文。
   - `depends_on`: 実装上の前提になるタスクがあれば。
5. `mcp__lightpm__pm_add` で登録する。`depends_on` には既存の ID しか書けないので、前提になるタスクから順に登録し、返ってきた ID を後のタスクの `depends_on` に使う。互いに独立なものは並行して呼んでよい。
6. 最後に `mcp__lightpm__pm_list` を呼び、登録したタスクを短くまとめて伝える。一覧は `/pm view` で見られることも伝える。

## ルーブリック

### 優先度（上から当てはめ、最初に合致したもの）

1. 基本機能。これがないと主目的の基本シナリオが最後まで通らない → `max`
2. 主要シナリオの一部が成立しない。またはデータ損失や重大なセキュリティ問題 → `xhigh`
3. 多くの利用者が困るが、回避できる → `high`
4. 影響が限定的、または回避策が明確 → `mid`
5. 見た目、文言、軽微な改善 → `low`
6. 将来の候補 → `xlow`

判定が割れたら低い方を採る。

### 種別

`feature`（機能の追加・完成）/ `bug`（期待と異なる挙動）/ `refactor`（挙動を変えない整理）/ `polish`（見た目・文言・操作感）/ `chore`（ビルド・設定・依存）/ `release`（リリース手順）

### バグ

`severity`（S0=データ損失・クラッシュ・セキュリティ、S1=機能が使えない、S2=回避策のある劣化、S3=外観・軽微）と `impacts`（影響を受けるタスク ID）を付ける。`impacts` が既存タスクなら優先度は表から自動で決まる。機能名しかないときは `impact_priority` にその機能の優先度を渡す。

## モッドが無効な環境

`mcp__lightpm__pm_*` ツールが見当たらない場合は、`docs/pm-directory.md` の形式で `.pm/tasks/T-xxxx.md` を直接作る。
