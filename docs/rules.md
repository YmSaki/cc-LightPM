# 優先度とフェーズの規則

次にやるタスクは、ここに書いた規則だけで決まります。
LLM が関わるのは、登録するときの分類（種別と優先度）だけです。

## 優先度

| 優先度 | 意味 |
| --- | --- |
| `max` | 基本機能。欠けるとプロダクトの主目的が成立しない |
| `xhigh` | 主要シナリオの成立に必要。データ損失や重大なセキュリティ問題を含む |
| `high` | 重要。なくても使えるが、多くの利用者が困る |
| `mid` | 通常。影響が限定的、または回避策がある |
| `low` | 改善、見た目、軽微な不具合 |
| `xlow` | あれば良い。将来の候補 |

分類では、上の表を `max` から順に当てはめ、最初に合致したものを採ります。
判定が割れたら低い方を採ります。
後回しにした作業はフェーズが進めば戻せますが、先走った作業は戻せないためです。

## バグの優先度

バグの優先度は、影響を受ける機能の優先度と重大度の組み合わせで決まります。
重大度は、`S0` がデータ損失、クラッシュ、セキュリティ、`S1` が機能そのものが使えない、`S2` が回避策のある劣化、`S3` が外観や軽微な不具合です。

| 影響先の優先度 | `S0` | `S1` | `S2` | `S3` |
| --- | --- | --- | --- | --- |
| `max` | `max` | `max` | `xhigh` | `mid` |
| `xhigh` | `xhigh` | `xhigh` | `high` | `low` |
| `high` | `xhigh` | `high` | `mid` | `low` |
| `mid` 以下 | `high` | `mid` | `low` | `xlow` |

`impacts` に既存タスクの ID を指定すると、指定された `priority` よりこの表の値が優先されます。
影響先がタスクになっていない機能なら、その機能の優先度を `impact_priority` に渡します。
RC 以降に `xhigh` 以上のバグを登録または再分類すると、自動でリリース阻害（`release_blocker`）になります。

## フェーズごとの着手できる下限

タスクが今のフェーズで着手できるかは、種別と実効優先度が次の下限を満たすかで決まります。

| フェーズ | feature | bug | chore | refactor、polish | release |
| --- | --- | --- | --- | --- | --- |
| Alpha | `high` 以上 | `xhigh` 以上 | `mid` 以上 | `xhigh` 以上 | 不可 |
| Beta | `xhigh` 以上 | `mid` 以上 | `mid` 以上 | `high` 以上 | 不可 |
| RC | 不可 | `high` 以上、またはリリース阻害 | `high` 以上 | 不可 | 不可 |
| GM | 不可 | リリース阻害のみ | 不可 | 不可 | 可 |

下限に満たないタスクは `deferred`（後回し）になります。
そのとき、着手できる最初のフェーズ（`defer.until`）と理由（種別ごと不可なら `P-KIND`、優先度が足りなければ `P-FLOOR`）が記録されます。
どのフェーズでも着手できないタスクは `post`（リリース後）になります。
この表は[設定](pm-directory.md#設定)で上書きできます。

**実効優先度**は、依存を考慮した優先度です。
タスクは、自分に依存している未完了のタスクの優先度を引き継ぎます。
たとえば `max` のタスクの前提になっている `low` の refactor は、`max` として扱われ、Alpha でも先に選ばれます。
後回しの判定は `pm_next` のたびに見直すので、後回しのタスクが後から `max` のタスクの前提になった場合も、すぐ todo に戻ります。

## フェーズを抜ける条件

着手できるタスクがなくなると、`pm_next` はフェーズを抜ける条件を確かめます。
満たしていれば、人間の承認なしに次のフェーズへ進みます。

- **Alpha → Beta**：`max` と `xhigh` の feature が未完了ゼロ
- **Beta → RC**：`xhigh` 以上の feature と `high` 以上の bug が未完了ゼロ
- **RC → GM**：リリース阻害の bug と `high` 以上の bug が未完了ゼロ
- **GM**：release タスクがすべて完了したらプロジェクト完了

どの条件も、作業中のタスクがないことを前提にします。
1回の `pm_next` で、条件を満たす限り GM まで続けて進みます。
フェーズは前にしか進みません。
戻すときは `/pm phase set` を使い、その操作は監査ログに残ります。
タスクが1件もないときは、フェーズを進めずに登録を待ちます。

## タスクの選ばれる順

着手できるタスクは次の順に並べ、先頭を選びます。

1. 実効優先度（高い方が先）
2. 推移的に妨げているタスクの数（多い方が先）
3. フェーズの主役の種別（Alpha は feature、Beta と RC は bug、GM は release）
4. 見積（S、M、L、未設定の順）
5. 作成日時（古い方が先）
6. ID

最後の ID が順序を一意に決めるので、同じ `.pm/` からは、読み込み順に関係なく常に同じタスクが選ばれます。
前提のタスク（`depends_on`）がすべて `done` か `dropped` になるまで、そのタスクは選ばれません。
