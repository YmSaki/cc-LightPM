# 優先度の決め方

## 優先度

| 優先度 | 意味 |
| --- | --- |
| `max` | 基本機能。欠けるとプロダクトの主目的が成立しない |
| `xhigh` | 主要シナリオの成立に必要。データ損失や重大なセキュリティ問題を含む |
| `high` | 重要。なくても使えるが、多くの利用者が困る |
| `mid` | 通常。影響が限定的、または回避策がある |
| `low` | 改善、見た目、軽微な不具合 |
| `xlow` | あれば良い。将来の候補 |

分類では、上の表を `max` から順に当てはめ、最初に合致したものを採ります。
判定が割れたら低い方を採ります。

種別は `feature`（機能の追加、完成）、`bug`（期待と異なる挙動）、`refactor`（挙動を変えない整理）、`polish`（見た目、文言、操作感）、`chore`（ビルド、設定、依存）、`release`（リリース手順）のいずれかです。

## バグの優先度

バグの優先度は、影響を受ける機能の優先度と重大度の組み合わせで決まります。
重大度は、`S0` がデータ損失、クラッシュ、セキュリティ、`S1` が機能そのものが使えない、`S2` が回避策のある劣化、`S3` が外観や軽微な不具合です。

| 影響先の優先度 | `S0` | `S1` | `S2` | `S3` |
| --- | --- | --- | --- | --- |
| `max` | `max` | `max` | `xhigh` | `mid` |
| `xhigh` | `xhigh` | `xhigh` | `high` | `low` |
| `high` | `xhigh` | `high` | `mid` | `low` |
| `mid` 以下 | `high` | `mid` | `low` | `xlow` |

`impacts` に既存タスクの ID を指定すると、指定された `priority` よりこの表の値が優先されます。
影響先がタスクになっていない機能なら、その機能の優先度を `impact_priority` に渡します。

## 一覧の並び順

一覧は、状態ごと（作業中、未着手、完了）に分けて、次の順に並べます。

1. 優先度（高い方が先）
2. 作成日時（古い方が先）
3. ID

最後の ID が順序を一意に決めるので、同じ `.pm/` からは常に同じ順に並びます。
前提のタスク（`depends_on`）は一覧に表示するだけで、並び順には影響しません。
完了の一覧だけは、新しく完了したものから並べます。

## 進捗と状態

タスクの状態は、`todo`（未着手）、`in_progress`（作業中）、`done`（完了）、`dropped`（取り下げ）のいずれかです。
進捗は、やることのチェックリストのうち済んだ項目の数で表します。
`pm_update` で状態を指定せずに項目を済みにすると、状態は進捗に合わせて変わります。

- 1項目でも済めば、未着手から作業中になる
- 全項目が済めば完了になる
- 完了したタスクの項目を戻すと、作業中に戻る
